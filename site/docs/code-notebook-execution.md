# CodeNotebook execution boundary

The CodeNotebook runtime is intentionally split by language. The shared
adapter contract is `prepare()`, `run()`, `cancel()`/`terminate()`, and
`dispose()`. A run returns a status, stdout, stderr, a bounded value, output
truncation state, duration, and structured diagnostics.

## Python

`createPythonAdapter()` creates no Worker and imports no Pyodide module until
`prepare()` is called. Preparation creates a module Worker from
`lib/code-notebook/python.worker.ts`; that Worker dynamically imports the
locally installed `pyodide` package and loads its files from `/pyodide/`.

Run code never crosses the main-thread boundary except as a structured message.
The Worker uses a null-prototype `jsglobals` object, so Python's `js` module is
not backed by the Worker global. It does not receive notebook context objects,
DOM references, storage, fetch, or host callbacks. Package discovery is not
called, so an import cannot trigger a CDN or package-registry request. The
Pyodide asset directory is generated by:

```text
pnpm prepare:pyodide
```

The generated `public/pyodide/asset-manifest.json` records the exact files and
byte count staged from the pinned npm package. `public/pyodide/` is ignored and
must not be committed. The central integration task should run the staging
script after dependency installation and serve that directory at the same
origin as the application.

Each run has a source-byte limit, a combined stdout/stderr byte limit, and a
wall-clock limit. A timeout, abort signal, or explicit cancel terminates the
Worker, discards the interpreter, and requires a fresh `prepare()` before the
next run. This is the reset boundary for code that cannot yield to Python's
event loop.

## Rust feasibility result

Rust remains a disabled capability with a real adapter seam. It does not call a
server, use Rust Playground, execute precompiled snippets, or claim that
`wasm-bindgen` is a compiler. The reproducible report is:

```text
pnpm spike:rust
```

The spike records the browser WebAssembly/Worker environment and the
production blocker. The checked candidates are:

- The official Rust `wasm32-unknown-unknown` target, which is a target for
  already-installed `rustc`, not a browser distribution of `rustc`/LLVM.
- `wasm-bindgen`/`wasm-pack`, which bind and package Rust output after a native
  Cargo build.
- Rust Playground, whose documented architecture is a frontend, Axum backend,
  and Docker compiler containers.
- rust-lang/rust issue #62202, the still-unimplemented request to self-host
  rustc as Wasm.

Sources:

- <https://doc.rust-lang.org/stable/rustc/platform-support/wasm32-unknown-unknown.html>
- <https://github.com/rustwasm/wasm-bindgen>
- <https://github.com/rust-lang/rust-playground#architecture>
- <https://github.com/rust-lang/rust/issues/62202>
Until a maintained local compiler artifact passes a browser Worker compile,
execute, diagnostics, cancellation, and size/time-limit spike, the UI should
render Rust as unavailable and offer the structured blocker diagnostic.
